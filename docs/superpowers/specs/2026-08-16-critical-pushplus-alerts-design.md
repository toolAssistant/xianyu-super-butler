# 闲鱼关键故障自动恢复与 PushPlus 告警设计

## 目标

当闲鱼账号遭遇 Token 失效、风控、消息连接中断或自动发货失败时，系统先执行已有的自动恢复能力。只有自动恢复无法继续、必须人工介入时，才通过现有 PushPlus 渠道发送告警。普通聊天、正常发货和恢复成功不推送。

## 当前状态

- Docker 容器使用 `restart: unless-stopped`，进程退出后可自动拉起。
- Token 刷新流程已有 Cookie 重载、WebSocket 重连、密码登录刷新、人工滑块和风控冷却能力。
- 自动发货流程已有失败通知调用和平台确认发货补偿队列。
- 数据库中已有一个启用且包含 Token 的 PushPlus 渠道，但未通过 `message_notifications` 绑定账号。
- 直接绑定 `message_notifications` 会同时推送普通聊天和发货成功，不符合本设计的低噪声目标。

## 架构

新增独立的关键故障告警服务。它根据闲鱼账号的 `user_id` 查找该用户所有已启用的 PushPlus 渠道，不读取 `message_notifications`，因此不会改变普通消息通知行为。

告警服务负责：

1. 对标题和正文做敏感信息脱敏。
2. 查询持久化冷却状态，抑制重复告警。
3. 使用 HTTPS 调用 PushPlus，并对临时失败进行有限重试。
4. 仅在至少一个 PushPlus 渠道发送成功后记录冷却时间。

数据库新增 `critical_alert_state` 表，以 `(cookie_id, alert_key)` 为唯一键保存最近成功发送时间。容器重启后仍可防止相同故障重复推送。

## 自动恢复流程

账号连接或 Token 异常时按以下顺序处理：

1. 重新读取数据库中的最新 Cookie。
2. 使用现有 Token 校验与 WebSocket 重连能力重试。
3. 在频率限制内使用已配置账号密码刷新 Cookie。
4. 如果仍需真人滑块，创建人工验证会话并立即发送关键告警，正文包含公网控制页链接。
5. 人工验证超时或自动恢复耗尽后进入风控冷却，并发送最终失败告警。

不启用自动模拟滑块，不绕过闲鱼风控。真人验证完成后仍使用 Token API 校验 Cookie，只有校验成功才保存。

## 告警触发条件

- 创建人工滑块会话，自动路径已无法继续。
- Token/Cookie/密码登录恢复失败并进入风控冷却。
- WebSocket 连续失败达到阈值，密码刷新仍失败，准备重启实例。
- 自动发货未匹配规则或未获得发货内容。
- 卡密或图片消息发送失败、部分发送失败。
- 卡密已发送，但闲鱼确认发货补偿达到永久失败或最长时限。
- 自动发货处理抛出异常。

正常发货、普通聊天、暂时性重连和自动恢复成功不触发关键告警。

## 去重与消息内容

- 默认冷却时间为 30 分钟。
- 账号级故障使用稳定的故障类型作为 `alert_key`。
- 发货故障使用订单 ID；订单 ID 缺失时使用聊天 ID、商品 ID 和买家 ID 组合，确保不同订单尽量独立告警。
- 发送失败不写入冷却状态，允许下一次检测继续重试。
- 消息包含账号、故障类型、自动恢复结果、人工操作说明、订单或商品标识、时间和人工验证链接。
- Cookie、密码、Token、`x5secdata`、`x5sec` 等敏感值不得进入告警或新增日志。

## 文件边界

- `utils/critical_alerts.py`：PushPlus 发送、敏感信息脱敏、告警编排和冷却判定。
- `db_manager.py`：告警状态表、PushPlus 渠道查询和告警状态读写。
- `XianyuAutoAsync.py`：在自动恢复与自动发货的最终失败节点调用关键告警服务。
- `tests/test_critical_alerts.py`：告警服务、去重、重试、脱敏和业务触发测试。
- `docker-compose.yml`：暴露告警冷却与 PushPlus 重试参数，保留现有默认行为。

## 错误处理

- 没有可用 PushPlus 渠道时记录明确错误，但不影响主业务恢复循环。
- 单个 PushPlus 渠道失败不阻止其他启用渠道发送。
- 所有渠道都失败时不更新冷却状态。
- 告警模块异常不得中断 Token 刷新、WebSocket 重连或自动发货流程。
- PushPlus 响应只有 HTTP 成功且业务码为成功时才视为发送成功。

## 测试与验收

自动化测试覆盖：

- 无 `message_notifications` 绑定时仍能找到账号所属 PushPlus 渠道。
- 同一故障在冷却期内只发送一次，容器重启后的数据库状态仍有效。
- 不同订单的发货失败分别告警。
- 发送失败不写入冷却状态，有限重试次数正确。
- 普通聊天、正常发货和恢复成功不触发关键告警。
- 验证链接保留，敏感字段被脱敏。
- 现有验证码远程控制测试继续通过。

部署验收包括：

- 构建并重启 `xianyu-app`。
- `/health` 返回 `healthy`，账号处于 `connected`，Token 状态为 `success`。
- 通过当前 PushPlus 渠道发送一条标注为测试的通知。
- 公网首页继续返回 HTTP 200。

## 范围边界

本设计不增加宿主机外部监控。整台 Mac、Colima、Docker 或本地网络完全停止时，应用自身无法发送 PushPlus。应用进程退出由 Docker 自动重启；应用仍运行但业务连接异常、风控或自动发货失败属于本设计覆盖范围。
